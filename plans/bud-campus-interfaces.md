# خطة واجهات BUD Digital Campus

## الهدف والتسليم
تصميم وتنفيذ 18 شاشة إنكليزية احترافية لعرض مشروع التكامل الجامعي على رئاسة The British University in Damascus، وتسليمها بصورة قابلة للتصوير والاستخدام في المونتاج. لا يشمل العمل إنتاج الفيديو أو النص الصوتي أو بناء نظام إنتاجي أو الادعاء باستبدال أنظمة الجامعة الحالية.

التسليم الأساسي الممكن داخل هذا المشروع هو معرض واجهات React عالي الدقة، مع وضع عرض نظيف لكل شاشة، وحالات تفاعلية محلية. لا يُعد ذلك ملف Figma بطبقات قابلة للتحرير. تسليم صور فعلية أو ملف Figma لا يُدّعى إن لم يُنتج ويُتحقق منه؛ الصور تُصدَّر فقط إذا توفرت أداة التقاط مناسبة، وإلا يُسلّم معرض جاهز للالتقاط مع مقاسات واضحة. طلب طبقات Figma للمونتاج يحتاج مسار تحويل أو إعادة بناء مستقل، وليس وعدًا ضمن هذا التنفيذ.

## حقائق البيئة
- التطبيق الحالي صفحة React فارغة في src/App.tsx.
- React 19، Vite 8، Tailwind CSS v4؛ CSS العام في src/index.css.
- خادم المعاينة يعمل تلقائيًا؛ لا يُشغّل خادم إضافي.
- مصدر المتطلبات وثيقة BUD-Graduation-Project-Proposal-v2.docx، مع قائمة الشاشات المتفق عليها في المحادثة.
- الشعار المرفق صورة بخلفية بيضاء ويحتوي الدرع وBUD والاسم الرسمي الإنكليزي. يُستخدم كما هو، دون إعادة رسم أو تشويه أو إزالة أجزاء الهوية الرسمية.

## الاتجاه البصري المعتمد
هوية أكاديمية معاصرة: كحلي مستوحى من الشعار (#102945 تقريبًا)، أحمر جامعي (#A51F2B تقريبًا)، خلفيات عاجية فاتحة (#F5F6F8)، أبيض، وحدود رمادية ناعمة. هذه قيم واجهة مستلهمة وليست دليل ألوان رسميًا. الأحمر للهوية والقرارات المهمة، مع أخضر للتحقق وذهبي للتحذير؛ لا يُعتمد اللون وحده للدلالة.

لوحة الرئاسة تحتوي مساحة قيادة كحلية ورسومًا فاتحة مقروءة، وبقية صفحات الإدارة وتطبيق الطالب يغلب عليها الطابع الفاتح. الخط الأساسي Inter من Google Fonts، مع أوزان واضحة. لا تُستخدم مؤثرات نيونية أو زجاجية مشتتة أو صور عامة توحي بأنها مباني الجامعة. الشعار على مساحة بيضاء بوضوح وتناسب أصلي؛ استخدام النص BUD Digital Campus في التنقل الضيق بدل تصغير الشعار الكامل حتى يفقد الوضوح.

ويب 1920×1080، وموبايل 390×844 بوحدات CSS، مع إمكانية احتواء الإطار في المعاينة دون تغيير نسبه. هذه مقاسات تصميم وليست ادعاء دقة تصدير. أسماء الشاشات والأزرار والبيانات إنكليزية؛ العربية المستخدمة هنا تخص الخطة فقط.

## البيانات المشتركة
جميع الأرقام والطلاب والقرارات أمثلة، مع مؤشر Demo data في المعرض ووصف مرافق للتسليم. بيانات ثابتة بلا توليد عشوائي. الفصل Fall 2026؛ الطالبة Maya Haddad، الرقم BUD-2024-0187، السنة الثالثة Software Engineering، GPA 3.62. تستخدم جميع الصفحات نفس المقررات والطالب والفواتير والمواعيد.

السيناريو المالي: 12 ساعة مسجلة بتكلفة تجريبية 100 وحدة USD للساعة، ورسوم خدمات 100، وإجمالي أولي 1300، ومدفوع 800، ومتَبقٍ 500. إضافة مقرر من 3 ساعات تجعل الإجمالي 1600 والمتبقي 800. هذه ليست رسوم الجامعة الحقيقية. يتصل مقرر Database Systems، الرمز CS301، ونتيجته 87، بجدول الطالب واعتماد العلامات. يتصل القرار DEC-2026-014 بإعلان التقويم الأكاديمي، لا بقرار رسمي حقيقي.

## هيكل التنفيذ
- src/App.tsx يدير المعرض، الشاشة النشطة، اختيار Web/Mobile، ووضع Presentation الذي يخفي جميع أدوات المعرض.
- src/index.css يضم الخط والرموز اللونية والأنماط العامة اللازمة مع Tailwind v4.
- فصل الشاشات والمكونات والبيانات في ملفات تحت src عندما يبرر الحجم ذلك: components للتنقل والبطاقات والجداول والرسوم وحالات التأكيد، screens للويب والموبايل، data للبيانات، وحالة مشتركة typed للديمو.
- حالة محلية React تربط التسجيل والفاتورة والعلامات والقرارات والنقل والوثائق. لا Backend أو API أو تسجيل دخول حقيقي. إعادة تحميل الصفحة تعيد الحالة الابتدائية؛ زر Reset demo يعيدها أيضًا.
- اختيار شاشة مباشر عبر رمزها؛ دعم معلمة عنوان مثل ?screen=W01&present=1 لفتح لقطة محددة. القيمة غير المعروفة تعود إلى W01 ولا تسبب شاشة فارغة.
- العرض الأساسي واسع، والموبايل في إطار ثابت بلا متصفح أو زخرفة هاتف تحجب المحتوى. في مساحة أصغر يتم احتواء الإطار؛ واجهات المونتاج ليست مشروع responsive مستقلًا لكل دقة.
- أزرار التجربة تؤدي وظائف محلية واضحة، وما هو خارج النطاق يُوسم بوضوح ولا يُقدم كوظيفة حقيقية. لا أزرار تصدير زائفة ولا روابط ميتة.
- الرسوم تُبنى بـSVG لتبقى حادة ومضبوطة، والأيقونات من نظام واحد متاح أو SVG موحّد؛ لا إيموجي.
- أي عنصر منبثق يمكن إغلاقه، مع دعم لوحة المفاتيح والتركيز وحالات hover/focus. احترام prefers-reduced-motion؛ الحركات قصيرة وغير لازمة للتقاط الشاشة.

## خطوات العمل
1. تحميل تعليمات تصميم النظام المناسبة قبل تعديل الواجهة، وتجهيز الشعار كأصل محلي بالمسار الناتج من أداة المرفقات، دون الإشارة لمسارات tmp في التطبيق النهائي.
2. تنفيذ اتجاهين بصريين مصغرين على W01 وM01: Academy Light وExecutive Contrast، ثم اختيار Executive Contrast للرئاسة وAcademy Light للطالب كافتراضي مهني إن لم يطلب المستخدم تغييرًا. لا يُكرر تصميم الشاشات الثماني عشرة في اتجاهين.
3. تثبيت مكونات الهوية والتنقل والبطاقات والجداول والرسوم.
4. تنفيذ شاشات الويب السبع، ثم شاشات الطالب الإحدى عشرة، مع مراجعة الترابط أثناء التنفيذ.
5. تنفيذ الحالات الثماني ووضع العرض وإعادة الضبط وروابط الشاشات.
6. تجهيز فهرس التسليم بأسماء W01–W07 وM01–M11 وحالاتها والمقاسات، مع توضيح ما أُنتج فعليًا وما يحتاج تصديرًا أو عمل Figma خارجيًا. لا إنتاج فيديو أو نص أو وعود بطبقات غير موجودة.

## التحقق ومعايير القبول
- تظهر الشاشات الـ18 كاملة بأسمائها، ويمكن الوصول إليها دون تغيير ملفات الكود.
- ترابط الأرقام وأوقات المحاضرات والعلامات والفواتير بين صفحات الويب والموبايل.
- فحص السيناريوهات الثمانية من الحالة الابتدائية وبعد Reset demo، ومنع تكرار العمليات المؤكدة وحجب النتائج غير المنشورة.
- مراجعة الإطارات المستهدفة لعدم قطع النصوص أو تزاحم العناصر، وضوح الرسوم والعناوين، نظافة وضع العرض، وسلامة الشعار.
- الخريطة موسومة تخطيطية؛ البيانات والوثائق تجريبية؛ الدفع الإلكتروني والتتبع الحي ليسا وظائف نشطة.
- للتغيير الشامل تشغيل pnpm build وفق سكربت المشروع، وتشغيل أداة التنسيق المقررة pnpm format على الملفات المعدلة فقط إن كانت تدعم ذلك. لا تشغيل خادم تطوير إضافي. الفحص البصري أو التقاط الصور فقط عبر أداة متاحة؛ لا ادعاء تحقق لم يُجرَ.
- أي تعذر في تصدير الصور أو إنشاء Figma يُذكر صراحة مع تسليم المعرض، ولا يُخفى بوصفه ملف تصميم مكتملًا.

## خارج النطاق
تنفيذ النظام الحقيقي، تكاملات الجامعة، بوابات الدفع، خرائط حقيقية غير مزودة، تتبع GPS، خدمات إرسال إشعارات، وثائق رسمية، الفيديو والصوت، ونسخة عربية كاملة. النصوص والمكونات تُفصل بشكل يسمح بإضافة لغات لاحقًا، دون ادعاء اختبار RTL في هذه المرحلة.
